Motion planning in control-point space

Planning an arm motion means finding a path through obstacles while accounting for joint and motion limits. Planigo represents the whole motion as a cubic B-spline in joint space and optimizes its free control points on the GPU using mixture-model information-geometric optimization (MGIGO). After a single solve, analytic retiming adjusts the trajectory duration without changing its geometry.

This page presents the offline, full-horizon planner: a complete trajectory from a fixed start to a selected inverse-kinematics goal. The demonstrations below replay precomputed plans; the browser does not run the optimizer.

Method

From a compact curve to a complete motion

01 Represent the motion

Feasible IK endpoints are ranked by a 64-sample reference-path score. Twelve control points describe a continuous joint-space curve. Six free, seven-dimensional controls are optimized; the endpoints remain fixed.

Cubic B-spline · 42 optimization variables

02 Optimize on the GPU

MGIGO samples candidate controls, evaluates their costs at 32 waypoints in parallel, and updates a Gaussian mixture for each free-control block.

120 iterations · 300 samples per iteration

03 Evaluate the complete motion

After analytic retiming, a C++ CPU evaluator checks the complete trajectory for goal accuracy, collisions, joint limits and dynamics. The number of evaluation samples grows with the final physical duration, including both endpoints.

N = ceil(T / 0.025 s) + 1 · 101 samples for 2.5 s

Current full-horizon method, updated 2026-10-18. Optimization uses 32 waypoints; final evaluation uses a maximum 0.025 s interval. Method illustrations are schematic. Control points live in seven-dimensional joint space, not on the Cartesian end-effector path.

Which tasks are counted?

A task needs a Planigo IK endpoint that passes the shared pose, collision, map-boundary and joint-limit checks. The same retained task IDs are used for cuRobo. Reference IK can be replaced by a valid cuRobo fallback endpoint.

MPiNets excludes 45 tasks and MB excludes 0. This filter uses endpoint feasibility before trajectory optimization, never the final outcome. Every failed trajectory on the retained set still counts as a failure.

The cohort depends on Planigo’s IK procedure. cuRobo uses its own internal IK; its native failures on retained tasks remain in the comparison. No unavailable internal status is inferred.

What the timings include

Planning is synchronized host time including IK, optimization, retiming and trajectory production. Pipeline adds per-task scene preparation and final evaluation. Warmup, initialization and artifact writes are excluded. All medians and P90 values use the retained tasks, including planning failures.

The headline optimization latency is Planigo’s solver scope only. Use the planning and pipeline columns when comparing methods. The previous 15 October page used 300 iterations and 10 mm clearance; this run uses 120 iterations and 5 mm. Timing and success changes are not attributable to the C++ backend alone.

Each planner runs in a separate process, sequentially, with one warmup task per scene group. One seed provides no estimate of seed-to-seed variability.

Scope and limitations

Compact control-point optimization and analytic retiming make the planning pipeline straightforward to inspect. The current implementation nevertheless uses soft ranking costs and discrete collision evaluation. Independently selected block means are not guaranteed to form a feasible joint solution.

There is no swept-volume collision check, mandatory execution gate or validated fallback controller. These are offline research results, not evidence of safe real-robot execution. The current comparison uses two datasets, a shared valid-IK cohort, fixed configurations and seed42. Native IK, checker approximations and budgets limit conclusions about optimizer quality alone.
